For B, [PostgreSQL snapshot functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION) require the exporter transaction to remain open while sessions import. Existing direct TLS/relay connection is the candidate holder; the official execute_sql interface provides no pinned-session handle, so exporting in one tool call and assuming persistence in another is unsupported. Counts and ledger digest must come from the same imported snapshot, not a later live table view. Migration75/catalog pins and global role/ACL changes still need their own stable boundary and post-checks. Local pg_dump17.11 --help confirms --snapshot; pg_dumpall --roles-only has no synchronized-snapshot option. [pg_dumpall](https://www.postgresql.org/docs/17/app-pg-dumpall.html) covers global objects separately.

Sequences are another boundary: [PostgreSQL isolation guidance](https://www.postgresql.org/docs/17/transaction-iso.html) says their state is immediately visible and not rolled back. A shared row snapshot cannot promise exact point-in-time sequence state. Recovery would require explicit sequence-safety verification against restored keys/state, not silently treating it as the same row snapshot. B also does not capture later DML, prevent post-snapshot revocation, justify overwriting a newer shared target, or authorize an80-version upgrade. A bounded read-only recovery point and a safe live rollout/write window remain distinct decisions.
