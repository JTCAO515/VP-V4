# AGENT-009 development ledger port

SQL source: `lib/server/entitlements/subscription-ledger/development-schema.sql`, a private development candidate outside `supabase/migrations`. It is not a deployable or automatically applied migration.

Producer: private development ledger and Apple server verifier. Consumers: Main's future authenticated server composition and Native/Web snapshot parsers. No HTTP route, runtime registration, sales binding, role grant, credential discovery or live Apple invocation is added.

`subscription-entitlement/1` is closed (`contract.ts`). It has `sourceEnvironment: Sandbox | localTest | null`, `localTest`, `ownerId`, catalogVersion 3, policyVersion subscription-development-policy/1, `checkedAt: ISO UTC milliseconds | null`, `lifetimeMs: integer 0..300000`, `state: none | active | expired | revoked | reconciliation_required | unavailable`, `period`, `remainingCapacity:null`, `purchaseEnabled:false`, `runtimeCapacityEnabled:false`. Current authoritative snapshots only use Sandbox, localTest false. Local Xcode source is refused by the verifier; never upgrade local data to Sandbox or active. Unknown versions/states/extra keys fail closed. Transport cap is 8192 UTF-8 bytes via decodeSnapshotText; Native/Web subtract request RTT and monotonic elapsed time from the server lease; device calendar never decides active/expiry. Active requires lifetimeMs > 0. SQL computes floor(min(300000, verified.checkedAt + 300000 - serverNow, expiresAt - serverNow)); nonpositive becomes reconciliation_required. Nonactive states have lifetimeMs 0; error/reconciliation also have checkedAt null. Other successful states carry trusted query or verification checkedAt. Unavailable/reconciliation return no owner or period private fields; none requires a successful authoritative query.

`period` binds transactionId, originalTransactionId, productId, subscriptionGroupId, purchaseAt, expiresAt, revokedAt, descriptorId `Sandbox:<transactionId>`, catalogVersion and policyVersion. Period timestamps are ISO UTC with milliseconds. Effective interval is [Apple purchase, Apple expires). No 720h arithmetic. No capacity balance is claimed. Repeated restore/refund never changes the descriptor or its immutable catalog/policy/capacity snapshot. Revocation is monotonic. Only a distinct verified nonoverlapping renewal period creates another descriptor. Account rolling-window history remains in #227; this domain neither resets nor writes it.

`createDevelopmentVerifier()` with no composition always rejects before credential, filesystem, network or ledger access. A future trusted server root supplies #225's validated catalog object and an approved Sandbox SKU/group separately; today's real SKU/price remain null and no root binds them. `appleSandboxPorts` reuses the existing Apple SDK and root. Server verification checks both signed device evidence and current Apple getTransactionInfo signed readback. No public validated-decoded-claim constructor exists. In-process WeakMap evidence plus its AbortSignal/deadline lease gate the persistence adapter; serialized/forged candidates fail. Injected verifier/readback tests are behavioral tests, not crypto or real Apple proof.

The verifier snapshots #225's complete catalog and binding using plain property descriptors, rejects getters/proxies, validates and freezes the copy, and captures verify/readback/now function references before await. SDK results are copied from data descriptors into immutable scalar snapshots immediately after await. The requested transaction ID is independently retained and checked against current readback. Payload/catalog/port mutation across awaits cannot change admitted facts. No getter is executed to obtain evidence.

Verification control accepts a server-owned AbortSignal and integer timeoutMs 1..30000 (default 10000 total). Each await is deadline/abort guarded. Pre-aborted control calls zero ports. Cancellation before readback prevents readback. Stalled/late SDK/API completion never mints or persists a candidate; SUBSCRIPTION_INFLIGHT_UNKNOWN explicitly means the SDK may still finish because these SDK methods provide no true cancellation. No retry is made. Aborting or expiring an already returned candidate's lease refuses adapter apply before any SQL call. A SQL write already sent can have unknown acknowledgement and must reconcile independently.

`developmentLedger(query)` is private administrator composition. Apply takes a branded candidate and expected family epoch (0 for absent), returns `subscription-ledger-receipt/1`, stable identity, epoch, replayed, recorded/revoked. Unknown acknowledgement, conflict or CAS failure requires reconciliation/readback, never a new period identity or blind retry. Read needs a trusted authenticated owner from Main, never caller-supplied account. No ordinary role can call new subscription SQL; the existing service-role-only legacy RPC ACL is retained unchanged. SQL JSON is an internal admin boundary, not a signature verifier; do not expose it as an RPC.

Cross-ledger identity fence is now implemented in the isolated candidate, with no shared application. It replaces the actual `public.storekit_apply_verified_v1(jsonb)` body only after fixed known-before definition/source/owner/ACL/flags validation; an explicit authored body adds visibility and conflict checks. Fixed known-after pins verify that replacement retained signature, owner, SECURITY DEFINER, config, ACL and original return wire. Unknown body/metadata stops the candidate; no runtime string patch, bypass wrapper, trigger, grant or second identity ledger is introduced. The applied legacy migration/TS/catalog files remain byte-identical.

Both writers require READ COMMITTED; pinned REPEATABLE READ/SERIALIZABLE and unrecognized isolation are rejected as ENTITLEMENT_ISOLATION_UNAVAILABLE before writes because waiting on a mutex cannot refresh a pinned transaction snapshot. The real RPC negative vector verifies zero rows under unsupported levels. Both actual writers take `pg_advisory_xact_lock(hashtextextended('entitlement-transaction:' || environment || ':' || transactionId,226))` after their input eligibility validation and before any owner/family/row lock. Each then reads the other ledger for the same environment/transaction, including revoked/erased retained identities. Collision returns only ENTITLEMENT_TRANSACTION_CONFLICT, regardless of owner. Same-ledger replay still returns the original descriptor/policy/interval; no capacity refill or calendar extension. Legacy 720h queue/refund rules are preserved. The new writer's legacy-table SHARE lock and redundant subscription-only transaction lock are removed: ACCESS SHARE reads coexist with old INSERT RowExclusive. New order is shared identity -> subscription-owner -> family -> rows; legacy order is shared identity -> legacy-owner(34) -> rows. Erasure takes only its existing owner/family/row locks and retains period/transaction keys, so no inverse shared-identity wait is added. Tests cover both winner directions, foreign owners, independent IDs progressing before the other commit, and legacy-owner / erasure wait chains. Arbitrary externally batched multi-ID transactions are not a new supported composition; callers would need a separately specified canonical order.

FORCE RLS cannot turn a filtered empty result into proof of absence. Candidate installation requires the fixed definer owner postgres to have superuser or BYPASSRLS visibility. Both writer paths also inspect their effective principal/visibility at runtime and reject ENTITLEMENT_VISIBILITY_UNAVAILABLE when unsupported; the legacy check precedes auth helper access so an unknown non-bypass definer cannot silently proceed. A rollback-only existing-role/owner fault test proves an actual private row becomes invisible under FORCE RLS and the actual legacy RPC refuses rather than issues an old grant. No ordinary role or positive Native access is added. Installation is exercised only in an atomic owned-fixture transaction; this file remains a nondeployable development candidate.
