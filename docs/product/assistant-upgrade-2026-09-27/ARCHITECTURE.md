# Versioned integration seams for the personal assistant

This is the implementation contract under [ADR-0027](../../adr/ADR-0027-personal-journey-assistant.md), not an already available API. Each producer/consumer PR freezes concrete wire/SQL schemas and fixtures before activation. Keep the current native v1/v2/text/grounded and Trip versions compatible; do not mutate a v1 meaning in place.

## Responsibilities and authority

| Object | Responsibility | Must not become |
| --- | --- | --- |
| Conversation | Stable owner-scoped interaction stream; messages reference tasks and artifacts | An automatic new billable task per message or a transcript used as the only truth |
| Journey goal | Minimal intent, scope, progress and optional Trip link; references ServiceTasks | A duplicate Trip, new scheduler or same-named ServiceCase |
| ServiceTask / Turn / Attempt | Bounded deliverable / execution unit / actual cost-bearing attempt | Three interchangeable success or charging states |
| Result artifact | Versioned typed generated deliverable and basis references | Confirmed Trip data or copied unversioned UserArtifact |
| Profile / Memory / working context | Existing authoritative preference field / other explicit persistent fact / temporary input | A second hidden preference database |
| Trip / Proposal / Patch | Confirmed facts / immutable candidate revision / deterministic transaction | An LLM-writable document |
| Evidence / tool observation | Qualified source, observation, applicability and freshness | Model memory or implicit authority to publish |

Use existing tables where their semantics match. Minimal new records/columns belong to existing domain ownership and append-only migrations; avoid premature general graph/platform schemas. Account/Trip deletion and export include new conversation, goal, artifact, index and checkpoint references.

## Conversation and task association (VPJ-78)

Define a new assistant envelope with server-derived owner/session and stable conversation ID, message ID, client idempotency key, optional goal/task/Trip/selected-artifact references, and explicit supported input relationship. Preserve source revisions and a monotonic event cursor. Names and wire version are fixed in the implementation PR; no live version is assumed here.

Server validates ownership, membership, current policy/recipient consent and relationship. A follow-up, amendment, separate question and cancellation are distinct operations. Classification uncertainty may require one clarification; it must not silently charge or assign the wrong goal. Existing four-Turn/clarification-only limits stay frozen for old modes, while the new mode gains bounded continuation and versioned scope changes. Never reopen a terminal Turn; append a related execution for amendments.

Multiple task projections can be visible while the composer remains active. Concurrency is bounded by existing cost/actor controls. Maintain a single authority for message ordering and task status; iOS cached state is a projection. Session replacement/logout invalidates reads and late responses.

The first VPJ-78 intake slice freezes `assistant-conversation/5` at `GET/POST /api/chat/native/v5/conversation`. A POST has exactly `conversationId`, `messageId`, `idempotencyKey`, `policyId`, `locale`, `text`, `relationship`, `goalId`, `expectedGoalVersion`, `taskId`, `parentMessageId`, and `turnId`; nullable references are explicit JSON nulls. `independent_question` uses a new Turn ID and the existing text worker in the same admission transaction. `goal_start` creates a thin goal at scope version 1 without a Turn. `follow_up` and `amendment` require an existing goal, current scope version and parent message; an amendment increments the goal version atomically. A referenced ServiceTask must already exist for the same actor with current consent and visible root. No Trip or artifact reference is accepted in this wire version. A separate question may share the stable conversation without acquiring a goal or ServiceTask.

VPJ-81 conversation selection adds `GET /api/chat/native/v5/conversations` and optional single `conversationId` UUID on the existing conversation GET. The authenticated `list_assistant_conversations_v1` returns at most 20 owner/current-policy/same-current-consent summaries in creation-time/ID descending order, with an excerpt of the first still-visible message (up to 120 characters) and creation time. No pagination, search, policy migration, total count or historical-consent recovery is implied. Explicit absent/foreign/ineligible IDs fail uniformly rather than falling back to latest or creating a conversation; the default GET remains latest. Both reads retain the base text/session gates when the assistant producer is disabled. Native pins its resolved selection, clears drafts/pending goal/task/result/confirmation context synchronously on a switch, rejects responses from earlier selection generations, and uses the existing intake writer for subsequent messages to that ID. Same-selection transport/5xx read failures clear sensitive projections while retaining immutable pending intake/planning keys and drafts; authoritative denial, explicit selection and account replacement clear retry context. Temporary offline scope changes retain the selected ID only for the same retained account/epoch/generation as an immutable pending intake; replacement clears both. Return to latest performs a fresh read; relaunch starts at latest without persisting a local transcript or selection. Target, physical-device and whole-Issue acceptance remain separate.

The third VPJ-78 slice adds `GET/POST /api/chat/native/v5/goals/{goalId}/trip` for an explicit existing-Trip association. Native first reads the owner's existing Trip list, shows its title and current version, and requires a separate confirmation to link or retarget; unlink has its own confirmation. The closed POST carries an operation UUID, conversation/goal scope and link CAS versions, optional current goal message reference, selected Trip ID/head version and `confirmed: true`. Private `assistant_goal_trip_links` stores only Trip ID/version and source operation; append-only receipts retain the actor session and whether a native confirmation or a confirmed Trip deletion ended the link. Every change normally increments both linkVersion and goal scopeVersion. The ordinary cap is 10000; a terminal unlink or confirmed Trip deletion reserves version 10001, which old message amendments cannot consume, so old goal/action/result basis cannot stay current at the cap. Current readback rechecks owner, active text consent, selected Trip head, archive/deletion state and the matching action receipt; stale links remain visible as needing review, never current. After text withdrawal or when the v5 assistant producer flag is off, the Trip-authorized `GET /api/chat/native/v5/goal-trips` returns only the owner's linked goal/Trip IDs and CAS versions, and the same goal route still allows owner/session/CAS privacy unlink while refusing new links. The read-only privacy list uses a goal-ID cursor with at most 50 links per page and `nextCursor`; native offers Load more rather than silently truncating or imposing an owner-wide 100-link cap. Concurrent changes can shift this live list, so Refresh restarts from the first page; it is not a snapshot claim. The v5 native view exposes the minimal unlink control without restoring goal text or text consent. A recently reauthenticated, confirmed Trip deletion atomically ends only that Trip's goal links while queuing the existing tombstone; an exact request replay does not end them twice, a queued deletion rejects new links, and execution rechecks no goal/chat/Turn reference before deleting. The link operation and deletion admission take the Trip row lock before goal/link locks, then recheck CAS; finite deletion lock contention returns unavailable for a bounded retry and never reports completion. No Trip content is copied or changed by link actions. The #560 publisher's non-null Trip prohibition remains until its owner separately validates current membership **and** a task/result basis produced for that scope; a link alone is not permission to publish an old answer for a newly selected Trip.

`assistant_conversations`, `assistant_goals` and `assistant_messages` are private, RLS-enabled, append-only migration tables. The conversation row serializes message sequences; the owner/idempotency key locks and a digest reject changed retries. `GET` returns the latest authorized conversation, 50 most recent messages in ascending sequence, at most 100 goals, and `nextSequence` as the durable cursor. The source Turn remains the authority for answer/status, and revoked text consent hides the projection. Goal edits remain `recorded` until a later explicitly accepted execution path exists; they do not start a worker, settle a charge, change a Trip, or make a result artifact. Native `assistant_conversation_v1` is opt-in and preserves the old modes as the rollback path. New message intake and new text-consent acceptance require the environment-specific `VISEPANDA_NATIVE_{LOCAL,STAGING,PRODUCTION}_ASSISTANT_CONVERSATION=true` producer flag alongside the existing text policy gate; all producer flags default off. Policy readback and GET conversation remain available when this producer is disabled, retaining the base text runtime/policy, verified JWT, active native session, owner and current-consent checks. Withdrawal and the existing v1 task-cancel path remain reachable. The broader text runtime kill switch is not bypassed, and withdrawn content is never restored. Account deletion cascades these new association rows, while the broader all-user-data export/delete executor and Trip/artifact references remain separate acceptance work for #559 and related privacy tasks.

## Context and memory (VPJ-11 with VPJ-78/80)

Each dispatch reads the latest permitted goal/task basis, selected Trip revision, relevant explicit Profile/Memory revisions, selected result, required evidence and a bounded conversation summary. Reuse ContextPlan/assembler; version task-specific source permissions and budget policy instead of bypassing filtering. Existing fixed budgets are starting implementation values, not a suitable universal plan-size promise.

A context manifest records selected source IDs/versions, omissions and policy; logs contain no raw sensitive text or hidden reasoning. Summaries are derived caches and cannot override their sources. Recheck consent, relevance, expiry and revisions immediately before external dispatch and before publishing a usable result. Corrected or forgotten memory invalidates queued/checkpointed projections; never resurrect it via compaction or retry.

The second VPJ-78 slice adds a read-only `POST /api/chat/native/v5/context` preview with wire version `assistant-goal-context/1`. It accepts exactly one authorized `conversationId`, `goalId`, current `messageId`, `expectedGoalVersion` and up to three distinct explicitly selected `memoryIds`; it requires the separate environment-specific `VISEPANDA_NATIVE_{LOCAL,STAGING,PRODUCTION}_GOAL_CONTEXT=true` flag in addition to the v5 conversation gate. The server reads the existing owner/consent-checked conversation and only the selected IDs through the existing retrievable-Memory RPC. It checks current goal/message scope and selected Memory owner, consent, state, receipt and revision, applies a conservative text relevance rule to preferences, then re-reads those sources and the mobile session before returning the bounded ContextPlan manifest. Hard constraints are considered only when explicitly selected and must fit the existing fixed budget. The response contains source references, versions, hashes and omission reasons but no raw Memory management list, rendered prompt or provider payload. It is an ephemeral read result, not a persisted dispatch receipt. `readyForProvider: false` is an explicit boundary: producing this manifest is not evidence of model consumption or changed answers. Profile travel pace has only the existing local-planning purpose; Trip, result artifact, qualified evidence and ServiceTask basis are marked not integrated in this slice. A later dispatch must obtain its own recipient authorization and perform a fresh source/version check; this preview cannot authorize it.

Provider routes remain behind the current protocol/recipient/budget contract. A stronger or different model is a versioned evaluation choice, not a global provider change. Knowledge source publication and scope qualification remain independent of model-generated planning suggestions.

## Result artifacts (VPJ-79)

Minimal planned semantics: artifact ID, owner, optional goal/task/Trip association, closed content type, immutable revision, currentness/lifecycle state, basis references (including relevant input/Trip/memory/evidence versions), validated content and allowed typed actions. Initial types: comparison, journey draft, decision brief, change proposal reference, practical result. Reuse Proposal IDs/revisions rather than duplicating a confirmation payload.

The first storage slice freezes only `comparison/1`. `turn_private.result_artifacts` owns the current revision and withdrawal state; `result_revisions` stores immutable validated content and input sequence, the exact source Task Turn, goal scope, and explicit Memory revisions. That first slice reserved Trip fields and rejected non-null IDs/versions. `result_events` is an atomic ready/revised/withdrawn outbox in the same transaction. Only the internal service role can call the CAS/idempotent publisher and withdrawal functions; no user or model writer is exposed. Publication requires the latest source Task Turn to be completed with an answer; cancellation, failure or unavailable state blocks it. A later Turn makes the old result non-current even when the goal version is unchanged. Withdrawal remains available regardless of Task state. The read RPC rechecks the current mobile actor, source task/text consent, Memory eligibility, goal version and exact Task Turn. It returns `current` separately from `historicalReadable`; withdrawn or deleted-source content is unavailable. `GET /api/results/native/v1` accepts an optional artifact ID and revision and serves the same owner-scoped read to the existing VP conversation and materials view. The native card displays literal bounded text and no actions. The present materials view is a Library consumption seam in the old five-tab shell; VPJ-82/83 still own the Library/four-tab navigation. `journey-draft`, `decision`, `change-proposal-reference`, `practical`, real evidence basis, actual planning producer, event delivery, export executor and the complete four-tab/Web experience remain future contract work. No comparison in this slice is a real recommendation or a confirmable Trip change.

The second result slice uses #572's explicitly confirmed goal-to-existing-Trip link. Append-only migration `20260927055000` permits a Trip-bound `comparison/1` only when the current link and its `native_user_confirmed` receipt agree on owner, goal scope, operation, link version, Trip ID/head and unarchived/nondeleting state. Both the source assistant message and completed Task must originate after that link receipt; an older Task cannot acquire the Trip merely by adding a later message. The immutable revision pins the link operation/version. Retarget, unlink, Trip head change, archive and later Task work remove currentness; queued Trip deletion hides content and completed deletion cascades its rows. Null-Trip publication retains its prior contract. `GET /api/results/native/v1/trip?tripId=...` resolves only a current owned reference; Journeys then opens its exact artifact ID/revision through the same content reader used by VP and materials. This is a selected-Trip consumer in the existing native shell, not completion of VPJ-83's four-tab navigation or a real comparison producer. It does not write Trip content or create a proposal-confirm action.

When several goals have results on one Trip, the Trip reference reader checks newest candidates for current eligibility and returns the newest qualifying revision. It examines at most 64 candidates using the Trip/creation-time index; if older candidates remain beyond that bound, it reports unavailable rather than claiming no result exists. Exact artifact ID/revision reads remain available through the owner-checked content endpoint. A broader per-Trip index or pagination is future work if real volume reaches this limit.

Creating/editing an artifact changes an owned draft, never a confirmed Trip. A selected route and a confirmed patch are different actions. Artifacts are readable through the same permission-checked service from native VP/Journeys/Library and supported Web surfaces. Search indexes hold derived references, with eligibility checks at query and open, and deletion/withdrawal invalidation.

VPJ-82's multi-comparison consumer uses `GET /api/results/native/v1/search?query=...&cursor=...` and the read-only `search_result_artifacts_v1` RPC over existing private results. Literal title/summary matching is limited to 120 UTF-16 units by HTTP/native; each page contains at most 20 current eligible comparison references, excerpts and exact Trip ID/version. SQL qualifies source consent, Task, goal, Trip/link/deletion and Memory basis before pagination. There is no total count or copied index/body. The emitted next cursor is the last eligible artifact ID in the returned page; incoming cursors are validated as owner-bound, current eligible comparison anchors, without a signature or proof of prior delivery; an absent, foreign, revoked or deleted anchor is uniformly unavailable and requires refresh. The owner/creation-time index bounds each raw keyset window to 128 candidates plus one sentinel before matching and qualification (and at most one cursor-anchor qualification). If an unscanned tail remains without 21 eligible matches for safe continuation, the response is unavailable, not empty or partial; no hidden-row cursor is exposed. The existing 10-second request deadline also fails unavailable. Native pages replace previous excerpts, bind scope/query/cursor, expire within 30 seconds including request time, and clear on account/query/background changes. Opening repeats the existing exact ID/revision read; returning from detail refreshes the current page. Other material families and external discovery remain outside this search contract.

Native components accept schema-versioned content and typed actions, not arbitrary model HTML, URLs or code. Validate location identity and media rights/provenance. Unsupported card types fall back to safe readable content; old clients must not hide fields and then confirm a different meaning. Production imagery is not generated concept art masquerading as a real place.

Task-directed result reopening uses `GET /api/results/native/v1/task?taskId=...`. The authenticated read-only RPC resolves at most 64 newest active artifacts for that owner/Task, validates each exact revision through `read_result_artifacts_v1`, and returns only its ID/revision/Task reference. Overflow reports unavailable; missing, revoked or non-current results never fall back to global latest. Native VP resolves this reference before the exact content GET on both open and refresh, matching Task, artifact and revision and fencing session/request generations. This does not change the 20-Turn task-history projection or authorise another task execution. VP result display is additionally bounded to a 30-second request-start window and current actor/epoch/request generation. Leaving VP or backgrounding clears the projection and invalidates late reads; return and explicit Refresh re-read the selected completed Task through this exact resolver, including when its cached body is absent. Expired content is hidden, and missing history remains unknown. These are reader lifecycle checks, not Memory recomputation or another execution.

Result privacy preparation now exposes service-only paginated `artifacts`, `revisions` and `events` through `result_artifact_export_owner_v1`. It exports physically retained comparison content and source-version references, excludes execution/credential/idempotency material and does not copy source bodies. Owner/section-bound keysets and terminal section markers follow the Conversation export convention. Consistent snapshot, all-module assembly, protected delivery and user-facing export/delete completion remain unverified executor work; ordinary result eligibility and existing deletion cascades are unchanged.

## Bounded execution (VPJ-80)

Extend the existing durable lease runner and attempt budget. State progression distinguishes accepted/queued/running/waiting-input/waiting-confirmation/paused/completed/failed/cancelled; concrete unions and transitions are versioned before migration. Business outcome, execution state, artifact currentness and accounting status remain separate.

Per execution step: load current authorized basis → select next allowed action → execute with deadline and cost budget → persist validated observation/checkpoint → decide finish, wait or another bounded step. Cap model/tool steps, retries, concurrency, elapsed execution and cumulative task cost. A long-lived goal is not a permanently held lease or continuous LLM loop. Persist progress before releasing a wait; resume via existing durable work infrastructure on authorized input/event.

Tool catalog initially exposes narrowly scoped evidence lookup, place/route reads, deterministic constraint evaluation, owned artifact preparation and a typed proposal-producing adapter. ToolRegistry currently rejects Trip/proposal/external-effect registration: change only a reviewed capability boundary with persistent idempotency/action receipts. The existing in-process Map is not durable replay protection. No confirm/payment/booking/email tool is introduced by this plan.

Compare alternatives using real supported data and deterministic budget/time/transfer checks. Missing opening/price/availability evidence remains unknown; an appealing early direction may still be delivered with its assumptions. Preserve unaffected choices and user-confirmed requirements during replanning. Do not use arbitrary model confidence as feasibility proof.

At-least-once execution can repeat provider calls; record each actual attempt and unknown cost. Logical task settlement, artifact publication and Trip application must be idempotent. Cancellation/revocation denies new effects, and ambiguous effects are reconciled before retry. A newer basis prevents an old worker from publishing a current actionable artifact.

## Events, rendering and proactive work

Extend existing durable event/replay semantics with task status, progress summary, artifact-ready/updated/invalidated and preference-change references. Checkpoint/status writes and their publishable events require an atomic or recoverable outbox-style boundary within current storage. SSE is delivery, never the only persistence.

Native stores maintain independent conversation, task-list and selected-artifact state. A slow task cannot freeze send/cancel/navigation; new events must not steal focus or scroll. Global current-journey context uses stable IDs and explicit scope, not raw URL text. Library uses existing tools and source records; it does not duplicate their domain logic.

Proactivity starts with accepted task outcomes and user-set follow-ups. Reuse #221 for actual delivery, deduplication, quiet hours, timezone, permission and journey freshness. Recheck current consent and revisions before dispatch. Scheduling eligibility is not proof of APNs delivery; unsupported transport stays unavailable. Recurrent fact monitoring waits for a verified source and purpose, and stops when the goal expires, is paused or cancelled.

## Compatibility and staged activation

1. Inventory concrete producers/consumers and old API semantics; add closed new schemas and negative cases.
2. Add storage/reader changes first, with forward/rollback checks, RLS and export/delete coverage. No applied migration edits or automatic conversion of old text into a new charged task.
3. Add disabled new execution/capabilities and synthetic coverage; then a bounded real target-environment chain.
4. Connect native consumers through the same APIs/events; keep Web a light same-Trip/result consumer.
5. Activate the four-tab shell after the supported path is functional. Old entry mappings and fallback retain access to new in-flight tasks/results.
6. Broaden supported tasks only after observed reliability/cost/UX results. Disable new producers for rollback; preserve confirmed data and honest read/cancel/reconciliation paths.

Interface work has a named producer, transport, persistence, native/Web consumer, deterministic validator, owner and rollback in every PR. A schema file or demo renderer alone is a preparation result.

## Commercial compatibility

Reuse catalog, official transaction verification, entitlement and usage ledgers. New subscription semantics require an explicit versioned transaction/renewal/grant model; never reinterpret the current one-transaction/720h Pass as auto-renewal. Until selected, exact price/capacity are development hypotheses and no store sale is enabled. User task capacity is separate from actual attempt cost; clarification, correction and system repair do not create accidental new purchases.

Keep commission metadata out of organic relevance scoring; disclose commercial handoff and coverage limits. A ranking regression changes commission while holding traveller/evidence inputs fixed and checks that organic relevance does not improve because of that change. Actual affiliate attribution/payment still needs its own evidence.

### VPJ-83 first native shell slice

The four-tab consumer shell is explicitly enabled with `-VisePandaFourTabShell` or the bundled `VisePandaFourTabShellEnabled` boolean (initially false); `-VisePandaLegacyShell` always selects the five-tab fallback. Within the new shell VP is the launch destination. VP delegates to the existing Ask mode, Journeys to Trip, Library to the existing Knowledge/result reader, and Memory to the authoritative saved-travel-pace/undo consumer. The shell owns navigation identity only. A scope/epoch change recreates tab-owned views and closes secondary entries; existing session/consumer late-response gates remain authoritative.

Every tab offers Search and More destinations. Search opens existing place and current-comparison search, with their current scope limits. More destinations preserves Ask, Trip, Knowledge, Memory, Profile (account/privacy/Pass/logout), Today, Tools and Explore in either shell. Entry-only `visepanda://` links map these names and the VP/Journeys/Library/account/privacy/purchase/logout aliases without executing writes. Query, fragment, credentials, entity paths and unknown entries fail closed; this is not Web universal-link support. The five-tab fallback retains the same task read/cancel and result consumers so rollback does not strand accepted work. Real Memory-driven result changes, undated-goal Journeys aggregation and target-environment/device acceptance remain separate; see `artifacts/VPJ-83/verification.md` and `unrun.md`.

Travellers can also choose “Try four-tab navigation” in More destinations without a launch argument, then return with “Use previous navigation”. This per-launch navigation choice is not persisted; neither switch cancels a server task, deletes an artifact or grants data/provider consent.

### VPJ-83 bounded Journeys reader

Journeys now reads goals from the existing current-owner/current-consent latest-conversation GET alongside the existing Trip v2 list, then checks each existing goal-to-Trip GET. Goal text/version and Trip identity/content keep their existing writers. There is no structured date field in this goal read; a goal may appear before a Trip without a date being invented. The client bounds conversation payload to 256KB and 50 goals (the existing goal SQL is unpaged), and never claims an all-account index. Missing/malformed or mismatched relation fields render unknown; only a current same-goal/version relation matching an owned Trip/head is linked. Publication rechecks policy and uses a 20s request-start deadline on an injectable monotonic uptime clock, including network time. Display and load share that clock; TimelineView only redraws. Scope/generation fencing and inactive clearing remain.

Open current VP conversation delegates to the existing VP entry. Saved-Trip taps capture ID and account scope, use the original Trip reload/select consumer and show unavailable on account change, cancellation, absent ID or failed exact selection; no other Trip is silently substituted. The adjacent optional Trip entry defaults to nil for existing callers and does not admit a writer or automatic confirmation. Local/UNRUN details are in `artifacts/VPJ-83/journeys-20261002/`; full #564/target/provider/device acceptance remains separate.

### VPJ-83 goal summary pages

Journeys now uses a separate owner/current-policy/current-consent latest-conversation summary GET, with 20 goals per UUID keyset page and no message body. Its additive read RPC keeps existing goal/link writers and canonical Trip currentness intact. Conversation next_sequence and a bounded (100 goals plus sentinel) goal/link-version digest pin cursor membership; malformed, foreign, withdrawn, changed or old-conversation cursors reveal no metadata. The candidate query reads 21 rows; two digest scans and up to 20 materialized original relation reads are additional bounded work. Live Trip head/archive/deletion eligibility is checked per page, not frozen by that membership digest. The client replaces pages, preserves the shared monotonic 20s read fence and resets pagination on Refresh/account change. New read indexes/ACL do not widen table access. Closed response shape and predecode 512KB limits prevent unrelated message metadata or unbounded content. Latest-conversation wording does not imply changing VP's independently selected conversation. See `artifacts/VPJ-83/journeys-pages-20261002/` for actual local evidence, rollback and target/device UNRUN.
