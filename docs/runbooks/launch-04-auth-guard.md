# LAUNCH-04 closed-beta session guard

The private Ask, Trip Canvas, Profile, and Copilot pages now resolve a server-side Supabase claim before rendering owner-scoped UI. A missing public SSR configuration, missing claim, expired session, or claim-read failure redirects to the password sign-in page with a strictly allowlisted local `returnTo`; it does not expose a protected route, distinguish account/provisioning state, or fall back to anonymous private data. Only exact `/visepanda/ask`, `/visepanda/ask/:uuid`, `/visepanda/trips/:uuid`, `/visepanda/profile`, and `/visepanda/copilot` return targets are retained.

Staging execution is operator-owned after LAUNCH-02: use redacted invited owner and other-user accounts; verify anonymous redirect, valid-session deep-link return, invalid password generic failure, expired-session redirect, removed-access denial, owner/other-user API denial, mobile and Arabic RTL. Do not record passwords, cookies, JWTs, Project refs, e-mail addresses, or screenshots containing private identifiers. The decision whether to introduce a durable `beta_allowlist` remains separate: it requires an explicit operator provisioning policy and RLS/schema review, not a browser-only state check.

Rollback is a normal revert of the guard and safe-return module. Until that revert is reviewed, keep the default behavior fail-closed to the sign-in/unavailable surface; do not restore anonymous access to pages that disclose owner-scoped data. This code does not create accounts, configure password auth, add a recovery/signup flow, or mutate a Supabase Project.
