## Rollback and stop conditions

Before any new-Production writes, keep the new worker/flags disabled and either retain the old alias under the approved maintenance gate or return aliases to the exact previously recorded deployment after verifying its old shared-DB binding. Do not assume an old deployment is safe solely by its SHA.

After new-Production writes, **do not point clients back to the shared Staging project**: that would strand new records, expose old project state and invalidate Auth/consent continuity. Stop new writes, disable worker discovery/claims and provider/commerce flags, retain both datasets, and choose an operator-approved forward fix or exact-ID reconciliation. A restore to an earlier point is only an isolated recovery candidate until post-point deletion, withdrawal, budget, entitlement and Storage-object changes are replayed and verified. Never bulk-restore revoked or deleted user data, rewrite migration history, erase receipts, reset balances or delete the old project as a shortcut. Roll back a faulty additive schema through a new reviewed compatibility migration; keep existing records and applied history.

Abort before cutover if project ref/region or env pairing differs, backup/restore proof is missing, migration drift exists, data provenance is unresolved, Auth identity continuity is unreviewed, any permission matrix leaks, native/worker Production code is absent for an enabled feature, or domain/consent/backup contracts are incomplete.
