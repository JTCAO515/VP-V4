# VisePanda Closed Beta 售卖内容与产品止损线

日期：2026-09-04  
状态：产品经营建议；数字是首轮决策阈值，不是统计定律或已有成绩

## 0. 一句话

> **VisePanda 把你的中国自由行想法、截图和订单整理成一份持续更新的 Trip，在规划、准备和旅途中说明现在知道什么、还缺什么、下一步可以怎么做；预订和付款仍由你在第三方完成。**

## 1. Closed Beta 到底交付什么

每位用户围绕 **一个 Active Trip** 获得一段连续体验：

1. 从一句想法或现有材料开始；
2. 形成/导入一份可修改 Trip；
3. 检查关键冲突、未知和准备缺口；
4. 对酒店/交通/门票提供受限比较和外部完成路径；
5. 在真实旅行事件前后继续使用同一个上下文；
6. 在变化时给局部恢复方案；
7. 无法确认时给诚实降级、核实路径或有限人工接回。

这里卖的是“连续推进”，不是无限聊天。Ask、Planner、翻译、讲解、酒店链接都是同一个结果的组成部分。

## 2. 一站式首发的正确范围

长期采用“旅程覆盖完整、能力深度不对称”，Closed Beta 则只验收三个 Episode：

| Episode | 首发必须有的结果 | 组件 |
| --- | --- | --- |
| Plan | 零散想法/材料 → 候选 → 可编辑 Trip → 局部 diff → 用户确认 | Explore/材料/Planner |
| Ready | confirmed Trip → 准备缺口 → 已知/未知 → 一个下一步 | 酒店需求解释/受控外跳、支付/网络检查卡 |
| Travel | Today 使用同一 Trip → 一次中英现场任务/讲解 → 用户报告变化后局部恢复 | 翻译、讲解、Recovery |

三个 Episode 要共享同一个 Trip，但不要求同一位规划期用户在 12 周内一定到达中国。用 Planning/Arriving/In-trip 三个队列分别验证阶段，另以至少一个真实跨阶段个案验证连续性；没有自然机会标 `not_observed`，不能记为失败。

## 3. 明确不卖什么

- 不卖“AI 保证这份行程一定可行”；
- 不卖酒店/机票/火车票/门票库存；
- 不代用户付款，不作为当前交易签约主体；
- 不因打开联盟链接就声称已经预订；
- 不承担 OTA、酒店、交通和景点的履约责任；
- 不承诺全国所有地点、所有实时状态或 24/7 人工；
- 不承诺西班牙语、俄语、阿拉伯语；当前只保证中英；
- 不承诺所有问题都有答案；承诺诚实说明已知/未知和接续路径；
- 不用“陪伴”承诺情感依恋、朋友关系或永远在线。

## 4. 酒店首发边界

酒店拆成两个首发层：

```text
Trip条件
 -> L1a 整理区域/酒店/房型需求与取舍
 -> L1b 只传实际验收能保留的日期/人数/酒店参数
 -> 显示来源覆盖、时间与联盟披露
 -> 跳转一个先通过落地验证的供应商
 -> 用户在供应商完成选择、支付和合同
 -> 可选导入确认单回到Trip
```

禁止状态捷径：

```text
link_generated != link_opened != user_says_booked
!= confirmation_imported != provider_verified
```

任何把 `link_opened` 显示成“Booked/已订”的错误，都属于立即暂停发布的安全/信任事故。

没有实时授权 API 时，不宣称仍有具体可售房型、最终价或退改条款。佣金不进入推荐排序；affiliate 关系在推荐或 CTA 附近中英清楚披露；参数落地验证失败时不开放 CTA。

## 5. 止损不是一个数字，而是五种不同决定

| 决定 | 含义 | 例子 |
| --- | --- | --- |
| Continue | 当前假设有行为证据，继续下一阶段 | 用户分享真实材料并回来解决第二个任务 |
| Narrow | 痛点存在但承诺太宽/人工太重 | 先只做 planning + readiness + in-trip recovery |
| Change channel/message | 人没找到或话术错，未否定产品 | Reddit 无回复，但创作者合作可带来合格对话 |
| Pivot segment/problem | 接触到了目标人，但痛点/信任行为弱 | 计划型用户无痛，已订行程检查型用户更强 |
| Pause/Stop offer | 风险不可接受，或两轮充分验证仍无行为/付费 | 外部订单状态错误；完成结果后无人愿意付费 |

不要因为两周社媒没增长就“停止产品”；也不要因为有人夸想法就继续烧 6 个月。

## 6. 唯一 canonical 的 12 周阶段门

以下数字是创始人资源有限时的 **可执行启发式**，用于触发复盘，不声称统计显著性。需求/付费分母只使用英语国际来华目标用户；中文在 B1 用于实体、翻译卡和本地展示质量，不把中文测试者混入商业需求分母。

| 阶段 | 最小可评估样本 | 继续信号 | 未过门先做什么 |
| --- | ---: | --- | --- |
| B0 问题/工作流 | 12 名合格目标用户 | ≥8 展示真实工作流/材料，且愿用自己的 upcoming Trip 试一轮 | 收窄用户/场景；不是加功能 |
| B1 可控任务 | 英文 10 条 + 中文 10 条完整任务 | 每组 ≥8/10 完成；金额/否定/对象严重误解=0 | 收窄失败任务/语言；不合并平均 |
| B2 免费邀请 Beta | ≥30 个 `started_trip` | ≥18/30 `activated_trip`；≥21/30 明确保存、编辑或有理由拒绝 | 只允许一轮预登记的入口/首结果修订，再开新 cohort |
| B3 真实付费 | 每 cohort ≥20 个 `price_opportunity` | 首轮 ≥5 净付费为继续信号 | ≤1/20 先诊断价值包/价格/时机；只改一个变量后再跑同规模 cohort |
| B4 生命周期 | ≥20 个真正到达下一自然节点的 `active_trip_window` | ≥12 无需重述核心条件即可接续；≥8 在行前/在途实际使用 | 若只规划有效，收窄陪伴主张，不杀规划价值 |

第 1–2 周的执行校准不是产品门：15–20 个 opt-in/public openings、3–4 次对话、1–2 次真实交付。没完成执行量就不得评价需求；某渠道在足量、合规投入后失败，只停渠道。

`activated_trip` 必须完成“输入→可讨论结果→保存/编辑/明确放弃理由”。只聊天、收邮箱、点赞或接受邀请不算。

只有官方 App Store IAP/StoreKit 已可用、用户已经体验核心结果后，才计算 `price_opportunity` 和真实购买。TestFlight sandbox、问卷愿意、口头“会买”、邮箱和私人转账都不算；尚不可测时标 `not_testable`。

B3 首轮 ≤1/20 只触发诊断，不立即停止。对价值包或价格只改一个变量后，第二个同样有效的 ≥20 cohort 仍 ≤1 净购买，才停止 **当前付费包**；它不自动停止规划产品。

回访分开记录：`organic_return`、`useful_triggered_return`、`founder_prompted_return`。前两者都可能证明产品价值；Founder 手工催回只证明服务介入。没有自然旅行节点标 `not_observed`，不能当流失。

## 7. 人工和成本止损

### 7.1 三种 Founder Minutes 不能混用

分别记录：

```text
first_result_minutes = 为一个用户形成首次结果的实际服务时间
weekly_service_minutes = 激活后每个Active Trip每周的正常支持时间
research_minutes = 访谈、记录和产品学习，不伪装成未来客服成本
```

同一用户的实际代办/查证计入 service；研究访谈单列。

| Cohort 2 后 P50/P90 | 决策 |
| ---: | --- |
| ≤30 分钟/Trip 首成果 | 有机会产品化 |
| 31–60 分钟 | 收窄模板、知识和工具，观察下降趋势 |
| >60 分钟且连续两 cohort 无下降 | 当前 App 自助模型不成立；改为高价 Concierge 或收窄承诺 |

Human Task 单独计费/配额，不能用 Plus 无限聊天补贴无限人工。

招募前必须设置 `weekly_support_minutes_budget` 和服务时段：

```text
max_active_trips = floor(weekly_support_minutes_budget / P90_weekly_service_minutes)
```

尚无 P90 时，首批最多 5 个 Active Trips；这是测量保护，不是长期容量结论。

### 7.2 AI/供应商成本

每个完成结果看总成本，而不是单次模型调用：

```text
cost_per_useful_result =
  models + embedding/rerank + maps/live APIs + storage/egress
  + failed attempts + monitoring + allocated human cost
```

建议初期门：

- 任何用户权益都设内部硬预算和退化路径；
- Free 用户的模型成本不能依赖“多数人忘记使用”；
- Plus 的 AI Guide 可以包含在订阅，但高成本工具/深度任务设公平使用和任务路由；
- 人工任务永不包装成 unlimited AI；
- 价格未最终确认前，用实际 P50/P90 usage 重算毛利。

不要因为模型 token 便宜就忽略人工、地图、供应商调用、客服、App Store 分成和失败重试。

### 7.3 现金硬上限

当前没有 JT 可投入现金和 runway 数据，不能负责任地替他写死金额。开始 12 周实验前必须填：

```text
B_cash_12w = 12周可损失现金上限
B_ads = 0，直到至少10位用户完成首个结果
B_provider = 供应商/API/工具上限
B_contractor = 人工/翻译/审查上限
```

任一预算达到 80% 时冻结新增承诺；达到 100% 时停止相关支出，除非 JT 明确重新批准。不能用未填预算的“先做再说”替代止损。

## 8. 安全、隐私与信任：立即暂停门

以下不等样本量，发生一次就暂停相关能力、保护用户、查明范围：

- 未经确认修改 confirmed Trip 或执行外部动作；
- 把酒店联盟链接点击显示为已预订；
- 代收酒店/交通款或使用未批准支付路径；
- 跨用户/跨 Trip 暴露材料、记忆、聊天或运营报告；
- 删除请求后仍从可控副本检索/个性化；
- 对 critical 健康/安全/入境/支付事实在无当前证据时给确定性执行指令；
- 通知透露锁屏敏感信息或旧账号/旧 Trip 信息；
- 员工/公司内容伪装成独立用户评价；
- 佣金改变推荐排序却不披露；
- 以“陪伴”为由使用依恋、排他、恐惧流失话术。

恢复前至少需要：影响范围、根因、阻断、回滚/修复、受影响用户处理、回归测试和重新开放批准。

## 9. unavailable 的业务止损与资产化

“不知道”本身不算失败。以下才是失败：

- VP 不知道却猜；
- 只显示错误码，没有下一步；
- 反复产生同一个 Gap 却不进入内容/工具决策；
- 承诺跟进但没有状态或下一更新时间；
- 人工研究成本无限增长。

每周报告：

| 指标 | 用途 |
| --- | --- |
| Honest no-answer rate | 是否在能力外仍硬答 |
| Safe-next-step completion | 降级后用户是否能继续 |
| Repeated Gap count | 决定知识/工具优先级 |
| Gap resolution time | 运营产能 |
| Follow-up acceptance/disable | 主动跟进是否值得 |
| Same-gap recurrence after resolution | 知识/检索是否真正改善 |

如果某一高频 Gap 连续两批无法低成本、可靠地解决，VP 应明确缩小公开承诺，而不是持续人工兜底。

## 10. 一站式范围的反功能堆砌门

一个新功能只有同时满足以下条件才进入首发：

1. 服务于至少一个黄金任务；
2. 读写同一 Trip 或明确提供外部 handoff receipt；
3. 有 `success / unknown / failed / cancelled` 状态；
4. 有中英体验和错误处理；
5. 有权限、证据、成本和回滚；
6. 能在真实用户任务中减少停顿、返工或风险。

不满足时，即使它“听起来像完整旅游助手应该有”，也后置。

多角色不分别拥有首页、人格、长期记忆或付费包；它们是 VP 内部能力。功能数量不是一站式 KPI。

## 11. 陪伴型止损

主动提醒的评价不是点击率最大化：

| 指标 | 危险信号 | 处理 |
| --- | --- | --- |
| Notification disable rate | 某类提醒大量被关闭 | 停该触发，访谈原因 |
| Useful action rate | 看了但不行动 | 内容/时机不对，降为 App 内 |
| Duplicate/incorrect trigger | 重复或引用旧Trip | 立即停触发器 |
| Memory correction rate | 同类记忆频繁被改 | 降低自动保存/缩短TTL |
| “creepy”反馈 | 用户不理解信息来源 | 显示来源、收窄记忆、重获同意 |
| Dependency language | 用户认为VP是朋友/唯一支持 | 改话术和设计，禁止强化 |

Beta 默认只做打开 App 后的 Next Step；Gap watch 仅 opt-in，Push 仅用户亲自设置的确定时间提醒，Live Activity 后置。每条消息说明为什么现在出现，并有稍后/关闭。

## 12. 决策总表

在第 12 周或达到相应样本后，按以下顺序决定：

1. **安全门失败**：立即暂停相关能力，不讨论增长。
2. **没有完成执行量**：补执行，不评价需求。
3. **找不到目标用户**：换渠道/细分人群。
4. **找到人但问题弱**：转问题/人群，冻结大规模开发。
5. **问题强但不交材料**：修信任/首值/数据最小化。
6. **有首值但不回来**：缩小“陪伴”主张，检查生命周期触发。
7. **回来但不买**：改付费包/价格/时机；首个 ≤1/20 只诊断，第二个同规模有效 cohort 仍 ≤1 才停止当前包。
8. **买但人工>60分钟且不下降**：转高价 Concierge 或收窄，不按 SaaS 扩张。
9. **行为、购买和产能同时成立**：扩大 cohort，再决定内容和交易深度。

### 当前 Offer 的正式停止条件

单项失败不再用 `OR` 杀掉整个产品：

| 失败 | 对应动作 |
| --- | --- |
| B0 问题弱 | Pivot segment/problem；冻结大规模建设 |
| B2 激活弱 | 只改首值/入口/信任一次，再测新 cohort |
| B4 只规划有效 | 收窄“在途陪伴”，保留规划产品 |
| 两个付费 cohort 均 ≤1/20 | 停当前付费包，重做价值包/价格/时机 |
| Service P50 >60 分钟且两 cohort 无下降 | 转高价 Concierge 或收窄，不按自助 SaaS 扩张 |
| 安全/隐私/虚假订单状态 | 立即暂停相关能力，不等待样本 |

只有在两个有效 cohort 中，**核心问题、首个有用结果，以及真实付费或可持续服务成本三类证据组合失败**，才停止当前“自助式一站式 AI 旅行管家”Program。停止后只能选择收窄到最强 Episode、转高价 Concierge、换目标用户，或停止投入；不得只换宣传语继续原样开发。

若多个信号在临界区，不做平均分。回看具体用户段、Trip 阶段和渠道，预先登记一次只改一个主变量的迭代；迭代后仍未越门才决定，防止 false kill。

## 13. 每周止损会议（45 分钟）

固定只回答：

1. 本周最强的行为证据是什么？
2. 最强反证是什么？
3. 是渠道、问题、信任、产品、价格、成本还是安全失败？
4. 哪个假设还没有达到合格分母，不能下结论？
5. 下周只改变哪个变量？
6. 什么条件下立即停？

输出只能是 `continue / narrow / change channel / pivot / pause / stop` 之一，并写清 owner、期限、预算和复核门。

## 14. 当前已确认和仍未填的参数

已确认：

- 一个 VP、一个 Trip 上下文、端到端旅程；
- 规划是主要能力之一；
- 酒店首发 L1a 需求/候选解释 + 经落地验证的 L1b 联盟外跳，不碰库存/支付/履约；
- 当前只做中英；
- 官方 App Store 支付，不走私人付款；
- unavailable 要诚实且能形成下一步/Gap；
- 陪伴是专业温暖连续，不制造依恋。

仍需 JT 在经营前填写：

- 12 周现金损失上限；
- Closed Beta 同时服务的最大 Active Trips；
- 人工任务每周容量和响应时间；
- 最终订阅/Trip Pass 商品与价格；
- 哪些通知类别默认仅 App 内、哪些可请求 push；
- 酒店先接 Trip.com、Booking.com 或两者的验证顺序。
